## Executive assessment

MatchForge has substantial reusable foundations: immutable provider sources,
provider-neutral identity and dated corrections, typed observations, scoped
capabilities, shared work/fencing, qualified history, coherent goal forecasts,
artifact lineage and callable post-match scoring. The main problem is incomplete
integration/adoption and missing qualified evidence, not absence of another data
platform. Retain those owners, the current champion and Rust simulation.

The operating audit distinguishes facts from aspirations: backend FotMob/PitchAPI
work has valid leases, all 13 stage routes remain LEGACY, running build identity
is unknown, migration `202611100200` is absent, and operating runtime registry and
post-match evaluation tables are empty. The complete source-backed result-to-
monitoring-to-candidate-to-independent-evaluation-to-approved-promotion loop is
not operating. Data adaptation through rolling history is a different behavior.

Football/storage counts below retain the 06:09–06:26 UTC audit scope; a
09:25 UTC check refreshed release/work gates after the pause.

There are 45 old LIVE rows with missing scores and no bound operational resources,
12,970 latest finished unbound provider observations, and 281 same-key fixture
candidate groups. These are separate populations, not promised new forecasts.
The investigated three-source group already has a common accepted representative;
its public-date association is unverified, so it is not a new merge proposal.
MC Oran's canonical 0–0 final is available, while the incompatible native-resource
relationship is still disclosed as partial/conflicting. Missing originals,
identity proof, source access and scientific qualification remain explicit gates.

## Recommendation and priorities

Option B reuses existing domain owners and adds demonstrated missing contracts.
Option A's independent defect-sized repairs remain useful, but alone cannot
satisfy complete streaming, disaster recovery and governed learning. Option C's
replacement identity platform, scheduler, broker, storage service or ML stack has
no measured necessity and increases migration/reproducibility risk.

1. Verify release/schema/work truth and preserve a complete recoverable file/DB
   closure before risky adoption or cleanup.
2. Diagnose current score/identity cohorts, preserve merged fixes and improve
   bounded backend recovery/fairness without guessing football facts.
3. Deliver committed events, SSR and table contracts in independent slices;
   remove each browser HTTP timer only after its replacement passes.
4. Reduce repeated evidence/backup growth through verified representations and
   incremental snapshots before any separately approved eviction.
5. Deploy authorized monitoring first; retain explicit source, feature, holdout,
   candidate and promotion gates. Future team/player/context features use the
   scoped companion handoff and do not require an unrelated scientific milestone.

[SSE reconnection](https://html.spec.whatwg.org/dev/server-sent-events.html) and
[PostgreSQL transactional notifications](https://www.postgresql.org/docs/18/sql-notify.html)
inform the proposed transport; durable event records and correctly ordered scoped
checkpoints supply replay. Browser push cannot replace an unverified provider
push interface. [Consistent PostgreSQL dumps](https://www.postgresql.org/docs/18/backup-dump.html)
plus exact referenced immutable files are the recovery basis. Proper comparisons
follow [proper scoring](https://doi.org/10.1198/016214506000001437) and chronological
independent evaluation within existing stricter MatchForge governance.

## Storage and recovery result

The `.local` metadata walk counted 4,036,851 files without scan errors: about
123.8 GB logical / 135.7 GB allocated file bytes. Remediation evidence dominates.
The operating DB is about 14.0 GB; all non-template DBs total 143.6 GB. Docker
volumes, DB sizes and APFS allocated extents overlap and cannot be blindly summed.
No comparable growth time series or accepted full-restore RTO was established.

Capped samples round-tripped exactly: ZSTD-3 stored 9.12% of sampled JSON and
21.23% of CSV, while Parquet/gzip benefited little. Registry hash grouping suggests
only 24.4 MB duplicate registered source bytes; a separate selected report pair
has 1.913 GB identical content. Neither proves unique physical reclaimability or
deletion eligibility. No cleanup or original-file recompression occurred.

Use existing consistent dumps plus complete referenced files, restricted encrypted
external snapshots, independent verification and periodic isolated full restore.
Daily backup opportunity and a one-day online RPO are proposals; actual age while
asleep/offline and measured recovery time remain visible. Destination/key custody,
retention and accepted RPO/RTO require an owner-scoped recovery decision.
