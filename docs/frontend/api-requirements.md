# Frontend API Requirements

Status: PROPOSED — Pending Repository Verification

## Purpose

Document the API capabilities required by the MatchForge frontend
without claiming that proposed endpoints or fields already exist.

Source: MatchForge Stitch PRD v2.1.0.

These recommendations do not change forecasting, simulation,
calibration, evaluation or production authorization policies.

## 1. Existing API reconciliation

Before defining new endpoints:

1. Inspect the actual repository routes and API schemas.
2. Record the existing endpoint paths and supported methods.
3. Identify existing request and response DTOs.
4. Identify current consumers and compatibility requirements.
5. Compare the implemented API with docs/api/openapi.yaml.

The proposed OpenAPI documentation is not proof of implementation.

Do not create duplicate endpoints merely to match Stitch's examples.

## 2. Fixture listing API

Requirement ID: FE-API-001
Status: PROPOSED

The frontend needs to retrieve fixtures by:

- date;
- competition;
- match status;
- pagination parameters.

Required response information:

- fixture identifier;
- competition and team identifiers;
- kickoff timestamp;
- actual match status;
- actual live or final score, where available;
- latest eligible published forecast reference;
- forecast availability;
- data freshness.

Forecast probabilities must not be generated by the fixture API.

A fixture with no eligible published forecast must not expose
probabilities from an unpublished candidate.

## 3. Forecast retrieval

Requirement ID: FE-API-002
Status: PROPOSED CONTRACT RECONCILIATION

Reconcile the existing implementation with the proposed route:

GET /v1/fixtures/{fixture_id}/forecasts/{forecast_id}

The API must retrieve an immutable published forecast.

Preserve the existing approved forecast distribution and hash.

Do not introduce a competing source of truth for probabilities.

## 4. Public forecast metadata

Requirement ID: FE-API-003
Status: PROPOSED

Evaluate exposing approved public fields:

- forecast_id;
- model_id;
- model_version;
- issued_at;
- knowledge_cutoff;
- forecast_horizon;
- canonical_probability_hash.

Model identity must reference the model used to produce the forecast.

Do not expose private model parameters, training data or
restricted provenance.

## 5. Public simulation evidence

Requirement ID: FE-API-004
Status: PROPOSED

Evaluate a public validation summary containing:

- simulation mode;
- validation status;
- engine version;
- validation artifact reference;
- eligible simulation count.

Detailed parity, convergence and tail summaries require an explicit
public-contract and disclosure decision.

Raw validation logs, private seeds and internal diagnostics remain
restricted by default.

Simulation evidence must reference the matching immutable forecast.

## 6. Forecast availability and history

Requirement ID: FE-API-005
Status: PROPOSED

The frontend needs to distinguish:

- published forecasts;
- unpublished candidates;
- pending simulation validation;
- failed or inconclusive validation;
- approved analytic-only exceptions;
- unsupported capabilities.

An unpublished candidate must not be exposed as a validated forecast.

A pending or failed replacement must not hide an older published
forecast that remains eligible for retrieval.

Provide immutable historical forecast references and revision metadata
where approved.

## 7. Capability availability

Requirement ID: FE-API-006
Status: PROPOSED

The frontend must derive market availability from the authoritative
backend capability state, approved product scope and qualified data tier.

Unsupported markets must not return fabricated probabilities.

Research-only capabilities must not be presented as production-ready.

## 8. Acceptance criteria

The frontend integration is complete only when:

- endpoint existence is verified against repository evidence;
- public schemas are versioned and documented;
- fixture listing cannot leak unpublished probabilities;
- simulation failure cannot publish an invalid forecast;
- previously published forecasts remain retrievable;
- optional enrichment failure does not change forecast probabilities;
- public and restricted diagnostic fields are separated;
- existing API consumers remain compatible;
- automated contract and authorization tests pass.
